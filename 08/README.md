Для выполнения задачи выбран отказоустойчивый kubernetes-кластер из семи нод:
- 3 master: по 4 vcpu и 8 гб ram.
- 4 worker: по 8 vcpu и 16 егб ram.

Общие ресурсы кластера:
- 44 vcpu.
- 88 гб ram.

Выбранная конфигурация позволяет:
- разместить 21 экземпляр приложения.
- восстановить кол-во реплик после отказа одной worker ноды.
- сохранить работоспособность control plane при отказе одной master ноды.
- оставить резерв для служебных ресурсов.
- развёртывать приложение в разных окружениях.

# 1. Расчёт ресурсов:

приложение состоит из БД, системы кеширования, frontend и backend.

| Компонент | Кол-во реплик | cpu на реплику | Ram на реплику | cpu всего | ram всего |
|---|---:|---:|---:|---:|---:|
| ДБ | 3 | 1 | 4 ГБ | 3 | 12 ГБ |
| кэш | 3 | 1 | 4 ГБ | 3 | 12 ГБ |
| frontend | 5 | 0,2 | 50 МБ | 1 | 0,25 ГБ |
| bckend | 10 | 1 | 600 МБ | 10 | 6 ГБ |
| Итог | 21 | — | — | 17 | 30,25 ГБ |

cpu: 17 vcpu
ram: 30,25 гБ
кол-во pod: 21 (при размещении каждой реплики в отдельном pod).
- без учёта служебных ресурсов Kubernetes и операционной системы.

# 2. кол-во рабочих нод:

базовая конфигурация workerноды выбраны:
cpu: 8 vcpU
ram: 16 ГБ

рассчёт:
cpu: 17 / 8 = 2,125 на 3 ноды
ram: 30,25 / 16 = 1,89 на 2 ноды

ресурсы 3-х рабочих нод:
cpu: 24 vcpu
ram: 48 ГБ
- определяющим ресурсом является cpu.


---
# 3. Резервирование:

отказоустойчивость - предусмотреть выход из строя одной рабочей ноды.

отказе одной ноды останется:
cup: 16 vcpu
ram: 32 ГБ

Оставшихся cpu ресурсов недостаточно для работы всех экземпляров приложения, добавь 1 ноду, используя принцип N+1.
Итоговое кол-во worker нод: 4

| Ресурс | Штатный режим | Отказ одной ноды | Требуется приложению |
|---|---:|---:|---:|
| CPU | 32 | 24 | 17 |
| RAM | 64 ГБ | 48 ГБ | 30,25 ГБ |

После отказа одной ноды оставшихся ресурсов достаточно для восстановления всех реплик приложения.

Для обеспечения отказоустойчивости БД и кеша их реплик необходимо:
- распределить по разным нодам (anti-affinity).
- предусмотреть репликацию.
- автоматическое переключение (failover).
- для БД обеспечить постоянное хранилище (PV,PVC).

# 4. Учёт служебных ресурсов:

Кластер кубера состоит из двух типов нод:

master нады — управление кластером.
worker ноды — выполнение пользовательских приложений.


1.
worker ноды:
- учитывать ресурсы ОС, container runtime и компонентов kuber.

| Компонент | cpu | ram |
|---|---:|---:|
| ОС | 0,2 | 512 МБ |
| runtime и kubelet | 0,3 | 512 МБ |
| CNI и kube-proxy | 0,2 | 256 МБ |
| мониторинг и логи | 0,2 | 512 МБ |
| резерв | 0,1 | 208 МБ |
| Итог | 1 | 2 ГБ |

после вычета служебных ресурсов на каждой рабочей ноде осанется:
cpu: 8 − 1 = 7 vcpu
ram: 16 − 2 = 14 ГБ

доступные ресурсы после отказа одной рабочей ноды:

| Ресурс | 4 worker | 3 worker | Требуется | Остаток при отказе |
|---|---:|---:|---:|---:|
| cpu | 28 | 21 | 17 | 4 |

итог - при отказе одной рабочей ноды, с учётом служебных расходов, ресурсов достаточно для восстановления всех 21 реплики.


2.
master ноды:
компоненты:

| Компонент | cpu | ram |
|---|---:|---:|

При выходе из строя одной ноды сохраняется кворум из двух оставшихся экземпляров etcd.
Пользовательские приложения на управляющих нодах не размещаются.

# 6. Упаковка в helm:

структура:
```
app/
├── Chart.yaml
├── values.yaml
├── values-dev.yaml
├── values-stage.yaml
├── values-prod.yaml
├── charts/
└── templates/
```

Для каждого окружения используется отдельный values, в котором указываются:
- реплики.
- ресурсы.
- параметры подключения к бд и кешу.
- сетевые параметры.
- параметры окружения.

frontend и backend развёртываться через deployment.

для БД и кеш предполагается использование statefulset или кубер-операторов с поддержкой репликации и failover.

Отказоустойчивое хранилище и балансировщики нагрузки должны быть предусмотрены отдельно.
